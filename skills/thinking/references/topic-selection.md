# 用户共鸣选题协议

目标是从用户已经想清楚的个人认识中，提炼出目标读者会觉得“这说的就是我”的选题。选题分析是知识卡与用户之间的桥，不是标题生成，也不是用传播套路改写知识卡核心。

## 一、底层方法

借鉴咪蒙公开方法论中可复用的部分：寻找自我表达与用户需求的交集；围绕同一个想法生成多个角度，淘汰第一反应式的普通说法；优先选择“意料之外、情理之中”的真实反差；通过采访、互动和发布反馈验证，而不是把“我觉得”当成用户洞察。

只借鉴用户洞察、角度生成和反馈验证，不模仿煽动愤怒、制造群体对立或夸大承诺的表达风格。原始经历、结论强度和证据边界必须保持不变。

生成前读取 [mimeng-topic-cases.md](mimeng-topic-cases.md)，用至少三个不同机制的案例校准：用户原话、真实反差、现场证据。只比较机制，禁止复用案例文案。

### 执行边界：严格执行什么，不照搬什么

公开流程还包括一次提出 50 个选题、四级采访、100 个标题、5000 人投票和发布后复盘。本 Skill 严格执行其中决定“选什么”的逻辑，但不把整套媒体团队产能原样塞进一张知识卡：

| 公开方法 | 本 Skill 的硬性执行 |
| --- | --- |
| 自我表达与用户需求取交集 | 任何建议都必须同时由卡片主张和具体用户处境支持 |
| 50 个选题，淘汰第一反应 | 默认内部生成至少 10 个真正不同的角度再筛选；用户要求深度选题时扩展到 50 个，不向卡片展示中间清单 |
| 四级采访，确认用户已知与想知道 | 优先使用用户原话、留言、访谈、多人相似反应和现场材料；缺少这些证据时必须标为待验证 |
| 选择意料之外、情理之中的角度 | 反差必须来自真实材料，且正文能够解释，禁止硬造冲突 |
| 一篇内容只完成一个目标 | 每条建议只解决一个问题或讲清一个误判，不塞入整张卡的全部价值 |
| 100 个标题、5000 人投票 | 属于标题包装与大规模测试，不在本模块执行；用户需要时另做标题测试，不能反过来代替选题 |
| 发布后复盘 | 把真实反馈写入最小闭环，用反馈决定保留、修改或放弃建议 |

因此，这不是对咪蒙整套工业化生产流程的逐字复制，而是对其选题判断链路的可检查实现。任何一项硬性执行缺失，都不能声称已按该方法完成选题分析。

## 二、先分析，再得出选题

先在内部完成下面的分析，不把过程写进卡片：

1. **锁定自我表达**：这张卡真正想说什么，最有证据的判断是什么；选题不能为了传播改变它。
2. **确定具体用户**：这个判断与谁有关，他在什么场景里卡住，正在承受什么损失、担心或冲突。
3. **区分已知与未知**：用户已经知道什么、仍想知道什么、真正有情绪或疑问的点是什么。没有采访、留言或真实反馈时，把这些当作待验证假设，不能冒充用户洞察。
4. **生成多个角度**：围绕同一主张内部生成至少 10 个真正不同的入口，主动淘汰第一反应、空泛主题和所有人都能想到的普通说法；不要看到一个用户问题就立刻改写成标题。用户明确要求深度分析时扩展到 50 个角度。
5. **寻找真实反差**：用户原来以为什么，卡片提供了什么不同判断；优先“意料之外、情理之中”，没有反差时不要硬造冲突。
6. **限定一个目标**：每条建议只完成一个任务——提供新角度、说清一个误判、解决一个具体问题或展示一种真实证明，不能把整张卡的所有价值塞进一个选题。
7. **筛选选题建议**：按用户相关性、共鸣强度、角度新鲜度、正文可兑现性和证据边界筛出 3–5 个建议。每条用一句人话说清“为谁讲、在讲什么矛盾、给出什么不同判断”，不加工成标题。

可用内部公式检查：

> 共鸣选题 = 自我表达与用户需求的交集 + 用户熟悉的具体矛盾 + 一个可兑现的新判断

参考笔记、模板和评测样例只能帮助理解结构。禁止复用其中的解释性标题、用户问题或选题建议；每一行都必须从当前知识卡及当前受众分析重新推导。

## 三、默认呈现

核心卡片之后只追加下面这段：

```markdown
## 选题建议

**目标读者**：{一句话写清具体人群与当前处境；若为推断，写“候选目标读者（待验证）”}

| 用户可能关心的问题 | 选题建议 |
| --- | --- |
| {用户会亲口问的具体问题} | {一句话讲清用户矛盾与不同判断，不写成标题} |
| {问题 2} | {选题建议 2} |
| {问题 3} | {选题建议 3} |
```

默认 3–5 行，最有真实用户依据、最贴近卡片核心的建议放在前面。用户需要自己比较时，不替他强行选定唯一答案；用户明确要求推荐时，再标出首选并用一句话说明理由。

## 四、两列怎样分工

### 用户可能关心的问题

- 使用第一人称或用户日常会说的话。
- 写具体目标、阻力或损失，不写“如何提升认知”“如何建立系统”等空主题。
- 每行代表一个不同的用户入口，不把同一个问题换词重复。
- 用户没有提供受众证据时，只能写“可能关心”，不能宣称已经验证。

### 选题建议

- 不写标题，不追求点击口吻；直接说明这条内容应该讨论的用户矛盾和核心判断。
- 必须先完成上面的选题分析与筛选，不能只换词复述左列问题。
- 共鸣至少来自一种真实依据：用户原话、多人相似反应、具体场景、真实损失或身份与现实的反差。
- 没有真实用户反馈时，建议仍是待验证假设，不能声称“用户一定会共鸣”。
- 必须由知识卡的真实经历、逻辑和边界完整兑现。
- 不使用虚构数字、虚假普遍性、羞辱、恐吓或人为制造的群体对立。

## 五、简洁约束

默认不要加入：

- 每条选题的“给谁、共鸣点、内容承诺、传播评分”等重复字段；
- 一段解释如何提炼选题的方法；
- 标题、标题评分或一组只有措辞差异的包装文案；
- 与“一句话、问题、解决方案、逻辑”重复的选题护城河说明。

只有用户明确要求深度选题分析时，才在对话中展开目标读者、验证证据、渠道和标题测试；不要把这些塞回知识卡。

## 六、检查

- 左列是否像目标读者会说的话，而不是创作者的行业术语？
- 右列是否经过用户、角度、反差、单一目标和证据筛选，而不是换词重复左列？
- 用户能否在建议里认出自己的具体场景、损失或说不出口的矛盾？
- “共鸣”是否有用户原话、多人反应、具体场景或真实反馈支撑；没有时是否诚实标为待验证？
- 建议是否来自当前卡片，而不是复用了模板、参考笔记或评测样例里的文案？
- 不看原对话，能否一眼比较不同建议所对应的用户入口？
- 每条建议能否由卡片正文兑现？
- 删除任何一行后，是否确实少了一个不同的用户入口？
